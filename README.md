# ESPED Resort frontend

React 19, TypeScript, and Vite frontend for ESPED Resort, connected to the LavaLust REST API with JWT bearer tokens.

## Requirements

- Node.js 20.19+ or 22.12+
- npm
- LavaLust backend running locally for API-backed pages

## Setup

1. Copy `.env.example` to `.env.local`.
2. Set `VITE_API_URL` to the backend base URL.
   - Local example: `VITE_API_URL=http://127.0.0.1:3000`
   - Use your own backend host/path if it differs.
3. Set `VITE_GOOGLE_CLIENT_ID` to your Google OAuth web client ID. Configure the same value as `GOOGLE_CLIENT_ID` in the backend environment.
   - Add the frontend origin (for example, `http://localhost:5173`) to the OAuth client's authorized JavaScript origins. The API origin (`http://localhost:3000`) is not the browser origin.
   - The Google client secret is not used by this sign-in flow and must not be added to frontend variables.
   - From the backend root, run `php lava migration run` to add the Google subject column.
   - An existing account with the same verified email is linked to that Google subject. Admin Google sign-in is disabled unless `ADMIN_GOOGLE_LOGIN_EMAIL` exactly matches the administrator's Google email.
4. Install dependencies and start Vite:

   ```sh
   npm install
   npm run dev
   ```

Vite proxies `/api/v1` to `VITE_API_URL` during development. Production requests use `VITE_API_URL` with `/api/v1` appended. If the backend is mounted under a URL path, include that path in `VITE_API_URL`. Do not put secrets in `VITE_*` variables: Vite exposes them to browser code.

## Booking spam protection

Password login, guest registration, and booking submission use Cloudflare Turnstile. Set `VITE_TURNSTILE_SITE_KEY` in the frontend `.env.local` and `TURNSTILE_SECRET_KEY` in the backend `.env`. Restart the Vite dev server after changing frontend environment variables. Register the frontend's actual browser hostname in the Turnstile widget settings. The backend verifies each token with Cloudflare and checks its action (`login`, `signup`, or `booking`); missing keys or verification-service failures block the request.

## Manual GCash deposits

The guest payment flow requests a 50% deposit calculated by the backend from the confirmed booking total. Guests transfer the exact amount to the resort's GCash account, then submit their GCash transaction reference. An admin must verify the reference and received amount in GCash before the booking shows the deposit as paid; this flow does not automatically confirm transfers.

Configure `GCASH_NUMBER`, `GCASH_ACCOUNT_NAME`, and `GCASH_QR_IMAGE_URL` in the backend `.env`. Use a real static QR generated by the resort's GCash app; a phone number alone cannot be converted into a valid GCash payment QR. This static QR identifies the receiving account, so the guest must still enter the server-calculated amount shown in the app. For example, put the QR image at `public/gcash-qr.png` in the frontend and set `GCASH_QR_IMAGE_URL=/gcash-qr.png`. Never use a QR image supplied by a guest.

After adding the payment migration, run `php lava migration run` from the backend root.

## Styling

The frontend uses Tailwind CSS 4 through its Vite plugin. See [docs/TAILWIND.md](./docs/TAILWIND.md) for setup details and the incremental UI adoption plan. Existing component styles remain in place while screens are migrated.

## Source layout

- `src/app/`: app composition, providers, route definitions, and app-level data orchestration.
- `src/features/`: feature-owned pages and API modules (`auth`, `booking`, `admin`, and `public-site`).
- `src/components/`: reusable feature-agnostic UI and layouts.
- `src/hooks/`: shared React hooks.
- `src/lib/`: shared API client and integration helpers.
- `src/assets/`: images and other imported assets.

Feature internals should stay private. Import another feature only through its `index.ts` public exports. Shared components, hooks, and libraries must not import from features. Use the `@/` alias for imports rooted at `src/`.

## API and authentication

All HTTP requests use `src/lib/api.ts`. Feature endpoints belong in their feature's `api/` module; app-level data loading belongs in `src/app/useAppData.ts`. The API client keeps JWT access and refresh tokens in memory and retries an authorized request after a successful refresh. Backend authorization remains authoritative.

The backend must provide the API routes and enforce authorization. When frontend and backend are deployed on different origins in production, configure the backend's CORS allowlist for the frontend domain.

See [docs/ACCESS-CONTROL.md](./docs/ACCESS-CONTROL.md) for role-based page access, backend authorization requirements, and a guest/admin verification checklist.

## Tests and collaboration

Application code uses TypeScript (`.ts` and `.tsx`). Run `npm run typecheck` to validate types; production builds run type-checking before Vite bundles the app. Unit tests live beside the code they cover and run with Vitest via `npm test`. Pull requests should run lint, tests, and a production build; the GitHub Actions workflow does this for pushes and pull requests.

Use focused branches such as `feature/booking-calendar` or `fix/service-search`. Keep changes within the feature folder when possible. Coordinate edits to `src/app/`, `src/components/`, `src/lib/`, `vite.config.js`, and `package.json`, since these are shared integration points. Use Conventional Commit prefixes (`feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`).

Add repository-specific owners to `CODEOWNERS` once the team has agreed on GitHub usernames; this project does not assign placeholder reviewers.
